## 一、架构设计总体原则

| 约束 | 说明 | 架构应对 |
|------|------|---------|
| **一套架构、一套规范** | 8个子产品统一技术底座、统一代码规范、统一部署运维体系 | 统一开发框架脚手架 + 统一依赖BOM + 统一规约（见《灵犀系统技术规约》） |
| **既可独立运行、又相互耦合** | 子产品可独立开发、独立演进；跨子产品能互联互通、数据共享 | 模块化单体起步 + 服务边界预留 + API契约驱动 + 事件解耦 |
| **支撑未来完整功能** | 一期P0（33项）起步，最终支撑234项功能 | 选型时预判峰值场景，组件能力一步到位 |
| **成熟稳定、开源优先** | 全部采用业界主流、社区活跃、有大规模生产验证的开源组件 | — |
| **扩展式、迭代式开发** | 按子产品、模块增量化交付 | 插件化模块 + 单应用路由分区/包边界 + 数据库变更脚本化 + 特性开关 |
| **中台与触点分离** | 独立站/营销前端等触点可独立仓库发布，但必须基于灵犀开放能力交互 | 触点层 + OpenAPI/Webhook/SiteConnector；详见第十一章与《触点独立站集成规约》 |

### 五条架构铁律

1. **服务边界即组织边界**：按子产品划分服务边界，边界之间只允许通过 API 契约和事件总线通信，禁止跨边界直连数据库。
2. **API-First**：任何模块对外能力必须先定义API契约（OpenAPI 3.0）再写实现。
3. **无状态水平扩展**：应用层无状态，会话、任务状态外置到Redis/DB，任何模块可通过副本扩容。
4. **默认异步**：跨模块的业务流转优先使用事件/消息，同步调用只用于强一致性读操作。
5. **配置外置**：一切环境差异、业务参数走配置中心，禁止硬编码。

### 2.2 架构形态：模块化单体 → 微服务的两阶段演进

| 阶段 | 形态 | 说明 |
|------|------|------|
| **一期（P0）** | **模块化单体（Modular Monolith）+ 独立专项服务** | 8个子产品在代码层面是**独立Maven模块**（一个monorepo），有严格的包边界和依赖规则；仅将"天然需要独立扩展"的能力（邮件触达通道、WhatsApp通道、LLM网关）拆为独立部署的服务 |
| **二期起** | **按子产品拆分微服务** | 当某个子产品负载或团队规模达到阈值时，将该模块整体迁移为独立微服务，对外API不变、事件不变，前端无感知 |

**平滑过渡设计要点**：
- 模块间通信从一开始就走**内部API接口（Java Interface）+ 领域事件（Spring Event → RocketMQ）**，单体阶段走进程内调用，拆分后替换为RPC/HTTP，业务代码零改动
- 每个模块独立数据库Schema（共库不同Schema起步，拆分时按Schema迁库）
- 统一使用 OpenFeign 声明式客户端接口定义跨模块调用，单体内直连实现，拆分后指向远程服务
- 前端为**单一 Next.js 应用**：8 个子产品以 App Router 路由分组 + monorepo feature 包划分，模块自治但统一发布，不做微前端

### 4.2 各公共服务职责定义

| 公共服务 | 核心职责 | 服务方式 |
|---------|---------|---------|
| **统一认证 auth-svc** | **基于 Casdoor** 的 OIDC/OAuth2.1 授权服务器；登录（账密/验证码/扫码）；JWT签发校验；SSO单点登录；M2M客户端凭证（智能体间调用）；Token吊销。Casdoor承载IdP职责，登录页/用户同步等定制由auth-svc封装 | SDK（过滤器/拦截器）+ 独立服务 |
| **统一权限 iam-svc** | **基于 Casbin（jCasbin）** 的统一权限模型：RBAC（角色-菜单-按钮）+ 数据权限（本人/本部门/本部门及以下/自定义，行级）+ 字段权限（敏感字段脱敏）；策略模型（model+policy）集中管理；权限决策API + 本地缓存SDK | 决策API + 注解SDK |
| **统一组织用户 user-svc** | 组织架构、岗位、员工档案；**员工主数据的唯一权威源**；与配置中心-用户管理打通（员工↔账号映射） | API + 事件（员工入职/离职/调岗事件广播） |
| **多租户 tenant-svc** | 租户生命周期（创建/套餐/停用）；租户级配置隔离与继承（平台默认→租户覆盖）；租户级资源配额（发信量、Token额度、存储） | 拦截器SDK（自动注入tenant_id）+ 服务 |
| **业务配置 config-svc** | 业务参数配置化存储与热更新（线索分配规则、公海规则、客户分层规则、发信策略、商机阶段定义）；底层LiteFlow规则引擎执行 | API + 配置订阅推送 |
| **消息通知 notify-svc** | 统一通知模型（通知类型/渠道/接收人策略模板）；渠道适配（站内信、邮件、WebSocket实时、未来APP推送）；分级推送（询盘P0实时、报表日报批量） | API + 事件消费 |
| **文件服务 file-svc** | 对象存储封装；预签名URL直传直下；图片处理（压缩/水印）；文件病毒扫描；引用计数清理 | API + SDK |
| **审计日志 audit-svc** | 统一操作留痕（谁、何时、何地、对什么、做了什么、改前改后值）；安全事件（异常登录、越权尝试）；日志检索 | 注解SDK异步上报 |
| **分布式ID id-svc** | 雪花ID + 业务编码规则（客户编码CUS-、商品SKU-、商机OPP-等，可按租户自定义前缀） | SDK本地生成（号段模式） |
| **统一检索 search-svc** | 索引管理（客户、线索、知识、沟通记录）；统一搜索API（权限过滤内嵌）；分词/同义词/多语言 | API |
| **任务调度 job-scheduler** | 定时任务注册/触发/分片；任务依赖编排；执行日志与告警 | 控制台 + SDK |
| **事件总线 event-bus** | 领域事件注册中心；发布/订阅管理；事件Schema版本管理；死信处理 | SDK（进程内Spring Event → MQ透明切换） |
| **LLM网关 llm-gateway** | 多模型注册与路由（按场景/成本/能力）；统一OpenAI兼容协议；Token预算与限流；调用日志与效果统计；降级熔断 | API |

### 4.3 公共组件库（代码级共享）

| 组件 | 内容 |
|------|------|
| **lingxi-dependencies（BOM）** | 统一依赖版本管理，所有模块强制继承，杜绝版本漂移 |

| 知识中心 | `lingxi-knowledge` | `/knowledge` | 统一发布 |
| 智能体中心 | `lingxi-agent` | `/agent` | 统一发布 |

| （专项能力） | `channel-email` / `channel-wa` / `channel-social` / `llm-gateway` | — | **独立部署**（触达与AI负载特性独立伸缩） |
| （智能体运行时） | `lingxi-agent-runtime`（Python 3.11 + LangGraph） | — | **独立部署**（智能体编排/RAG/工具调用，与业务Java栈解耦） |

> 一期实际部署单元：后端 `lingxi-monolith`（8子产品合一）+ 3个通道服务 + llm-gateway + **lingxi-agent-runtime（Python）** + lingxi-data-jobs + 公共服务（auth/iam/user等）；前端为**单一 Next.js 应用**整体发布。二期起按需把任一模块从monolith剥离为独立服务，模块代码不变。

### 5.2 子产品耦合的三大机制

**（1）API契约（同步能力复用）**

子产品对外能力以OpenAPI 3.0契约固化，注册到网关。

| 提供方 | API | 消费方 |
|--------|-----|--------|
| 数据中心 | 客户/商品/渠道/员工主数据CRUD | 业务运营中心（销售建档）、智能决策（客户洞察） |
| 知识中心 | 模板/话术/提示词检索API | 营销域（AI写信引用模板）、智能体（提示词加载） |
| 全球市场中心 | 搜索指数/热词查询API | 市场域（趋势分析页面）、市场分析智能体 |
| 配置中心 | 业务规则读取API（LiteFlow执行） | 销售域（线索分配）、营销域（发信策略） |

**（2）领域事件（异步业务流转）**

```
线索域:  lead.created → lead.assigned → lead.converted → customer.created
营销域:  campaign.launched → email.delivered/opened/clicked/replied
        wa.message.sent/received → visitor.identified
商机域:  opportunity.created → stage.changed → opportunity.won/lost
知识域:  template.published → script.updated
智能体:  agent.task.created/started/completed/failed → agent.insight.generated
```

**（3）共享主数据与统一上下文**

- 主数据（客户/商品/联系人/员工）**唯一权威源在数据中心**，其他子产品只读缓存或API引用，不重复建设
- 用户身份、租户上下文通过统一Token在所有子产品间透传（JWT携带 user_id/tenant_id/roles 摘要，完整权限走iam-svc决策）
- 前端通过全局上下文（用户、权限菜单、租户配置、i18n语言包）保证跨子产品一致体验

### 5.3 独立运行保障

| 维度 | 机制 |
|------|------|
| 独立开发 | monorepo内模块独立目录、独立Owner；前端按子产品划分 feature 包与路由分组，独立 lint/测试，共享统一构建流水线 |
| 独立测试 | 模块级单测+契约测试（Pact），公共Mock服务（auth/iam提供WireMock桩） |
| 独立部署 | 后端 K8s Deployment 按服务粒度；前端单应用滚动发布（Next.js standalone 输出），支持按路由分组/模块灰度 |
| 独立演进 | Feature Toggle控制子产品/模块级开关；租户级订阅控制（未订阅的子产品菜单不可见） |
| 降级隔离 | 通道服务故障不影响核心CRM流程（营销任务入队重试）；智能体故障回退人工流程（碳基兜底） |

### 6.2 数据库划分与多租户策略

|------|------|

### 6.3 核心数据域与主数据治理

| 数据域 | 权威源 | 关键治理点 |

## 七、AI与智能体技术架构

### 7.1 AI基础设施分层

```
┌────────────────────────────────────────────────────┐
│  智能体应用层：五大智能体（市场分析/社媒营销/潜客挖掘/  │
│               销售转化/智能决策）+ 工作台智能助手      │
├────────────────────────────────────────────────────┤
│  Agent Runtime层（独立部署，Python 3.11 + LangGraph）│
│   · 规划器（目标拆解/任务路由）· 记忆（短期会话+长期   │
│     向量记忆）· 工具调用（Function Calling/MCP）      │
│   · 多智能体协作总线（智能决策智能体作为协调者）        │
│   · 状态持久化与断点恢复（LangGraph checkpointer）    │
│   · Agent可观测（轨迹记录、Token计量、效果回流）       │
├────────────────────────────────────────────────────┤
│  能力层：RAG管道(文档→切片→embedding→Milvus→检索重排) │
│   · 提示词中心（版本/A-B测试，知识中心提示词管理实现）  │
│   · 内容安全（敏感词/合规检测，企业公约作为约束注入）   │
├────────────────────────────────────────────────────┤
│  模型层：LLM网关（统一OpenAI兼容协议）                │
│   · 模型注册：GPT/Claude/DeepSeek/Qwen/GLM可插拔      │
│   · 场景路由：写信→强写作模型；分类评分→轻量模型       │
│   · 降级熔断：主模型超时→备用模型→规则兜底             │
└────────────────────────────────────────────────────┘
```

### 7.2 Agent治理四角色

| 组件 | 技术栈 | 职责边界 |
|------|--------|---------|
| **智能体中心**（子产品） | Java（lingxi-agent） | 智能体配置/调度/监控的UI与元数据管理；模型注册/监控；技能与MCP目录；不做执行 |
| **Agent网关**（llm-gateway扩展） | Java | 模型路由、技能鉴权、租户配额、调用审计、熔断；智能体工具调用的统一出入口 |
| **Agent Runtime** | **Python 3.11 + LangGraph**（lingxi-agent-runtime，独立部署） | 规划、工具调用、多智能体协作、RAG执行、状态持久化、效果回写事件 |
| **业务域服务** | Java（各子产品） | 提供技能对应的业务API与MCP工具，**不内嵌第二套Agent框架** |

> 通信契约：Runtime → Agent网关（模型调用）；Runtime → 业务域（仅经注册的MCP工具/受控API，带用户与租户上下文）；业务事件 → Runtime（触发智能体任务）。

### 7.3 关键技术方案

| 决策点 | 方案 |
|--------|------|
| Agent框架 | **LangGraph**（状态图编排，checkpointer持久化，多智能体图协作） |
| 工具协议 | MCP（Model Context Protocol）作为智能体调用业务系统的标准协议；技能元数据注册到智能体中心（skillId/权限码/风险等级/Schema/超时/版本） |
| 结构化输出 | Function Calling + JSON Schema约束（Pydantic建模） |
| 问答式数据展示 | 意图识别 → 指标/维度/筛选词槽抽取 → 语义层(Semantic Layer)映射 → 受限查询API → 图表渲染 |
| RAG切片策略 | 话术/QA按条目；文档按语义切片（512-1024 token，15%重叠）；中英双语embedding模型 |
| 智能体兜底 | 每个智能体任务定义失败降级路径（AI失败→规则引擎→人工待办）；模型不可用回退模板/人工 |
| 碳硅协同 | 人工接管可中断/取消在途自动动作（如群发）；需确认步骤创建平台待办并回写Runtime状态 |
| 数据拉取任务 | lingxi-data-jobs（Python）：外部数据源拉取、限速、缓存、质量监控，与Runtime共用Python工程体系 |

### 7.4 连接器抽象（触达与外部系统统一接口）

邮件、WhatsApp、社媒、访客识别、客服渠道、支付、外部数据商、**独立站触点**等外部能力**统一抽象为连接器接口**，业务侧只依赖接口，不感知厂商：

| 连接器接口方法 | 说明 |
|---------------|------|
| `send / receive` | 出站发送与入站接收（消息/回调） |
| `accountHealth` | 账号健康度（Token有效期、信誉度、封禁状态） |
| `rateLimit` | 平台限频适配与本地频控 |
| `verifySignature` | 入站回调验签（HMAC） |
| `quota` | 配额查询（通道额度） |

**SiteConnector（独立站/触点，修订新增）** 在通用方法之上扩展：

| 方法 | 说明 |
|------|------|
| `registerSite` | 站点注册（tenantId、siteId、域名、渠道类型） |
| `pushCatalog` / `onProductChanged` | 商品镜像推送或变更通知 |
| `receiveOrder` / `receiveLead` | 接收触点订单与线索回传 |
| `rotateCredentials` | 站点 M2M 凭证轮换 |

约定：账号资产归数据中心数字资产管理，连接器只引用资产ID；渠道凭证由平台加密托管，永不出网关；更换厂商只替换连接器实现，业务代码零改动。独立站详细契约见《触点独立站集成规约》。

### 7.5 触点对话与经营智能体分工（修订新增）

| 能力 | 归属 | 说明 |
|------|------|------|
| 买家侧导购对话、站内订单查询 | 触点助手（如 SmartEva Eva） | 体验层；可调用开放技能 |
| 跨域经营编排、企业知识权威、五大智能体 | 灵犀 Agent Runtime | 中台层；经 llm-gateway 计量审计 |
| 模型 Key / 配额 | llm-gateway | 触点正式环境禁止散落直连多厂商（过渡期须备案） |

### 9.4 开发环境：云端 Docker 中间件 + 本地连接

| 环节 | 方案 |
|------|------|
| 中间件部署 | 云端 dev 集群（Docker Compose / 轻量 K8s）承载全部中间件，与 test/prod 环境隔离 |

| 凭据管理 | 连接凭据存放 Vault/本地环境变量，**禁止提交代码库**；本地默认使用**只读账号**，写操作走应用接口 |
| 数据管理 | 本地不落地业务数据；dev 库使用脱敏/样本数据；需要真实数据形态时由脚本从 test 导入 |
| 常用工具 | 数据库客户端（DataGrip/Navicat）经隧道连接；Redis/ES 管理端同样经隧道访问 |
| 容错兜底 | 连接池配置超时与断线重连；网络不可用时可启动 Testcontainers 本地轻量替代（仅限基础中间件） |

## 十一、触点层与独立站集成（修订）

本章为相对选型方案初版的**增补修订**，明确营销前端（独立站）与灵犀中台的关系。细则以《触点独立站集成规约 V1.0》为准。

### 11.1 定位

- **灵犀**：经营与数据中台（八大子产品 + 平台公共服务 + Agent Runtime）。
- **触点（如 SmartEva）**：买家侧展示、沟通、下单入口；**独立代码仓、独立发布**；通过开放 API / Webhook / SiteConnector 与中台交互。
- 触点**不是**第九个子产品，不得在触点内再造 MDM/CRM/IAM 权威。

### 11.2 交互原则

1. **禁止**触点与灵犀业务库互访（含只读 JDBC）；允许同机中间件，必须**独立 Database**。
2. **商品/客户主数据**权威在灵犀；触点保存镜像（`sourceId` + `sourceVersion`）。
3. **订单**：触点产生成交事实，幂等回传灵犀（挂线索/客户）；支付走支付连接器。
4. **B 端运营账号**统一 Casdoor + Casbin；C 端买家账号一期可留在触点。
5. **AI**：触点助手（Eva）= 对话壳；企业知识与经营编排 = 灵犀 Runtime / 知识中心；模型出口 = llm-gateway。

### 11.3 开放能力最小集

路径前缀：`/api/v1/open/site/**`（APISIX 开放分区）。  
P0：商品拉取、线索创建、订单回传/状态更新、知识检索、健康检查。  
请求头：在平台头基础上增加 `X-Site-Id`、`X-Site-Channel`。

### 11.4 与 SmartEva 现状的衔接

当前 SmartEva 与灵犀多为**基础设施共用**（如 `lingxi-postgres`），业务 API 尚未打通。应按《触点独立站集成规约》分期：P0 契约 → P1 Admin SSO → P2 商品单向同步 → P3 AI 合流 → P4 支付/存储对齐。
