# 灵犀系统 · 多智能体协作开发基础条件差距分析

> 日期：2026-08-20 ｜ 评估对象：WorkBuddy × Cursor 混合流水线方案（见 `灵犀系统-WorkBuddy-Cursor混合流水线方案.md`）
> 目的：对照方案要求的八项前提条件，逐项检查灵犀系统现状，判定是否具备启动自动派发的基础。

---

## 一、总体判定

**结论：工程骨架与文档基线已具备，多智能体协作基础设施层完全缺失。**

方案依赖的核心机制——"任务文件派发 + git/PR 回传 + 测试 Agent 验证闭环"——目前三项均有硬伤：
- git 仓库未初始化（回传通道断裂）
- 协作编排文件全缺（派发无依据）
- 测试框架近乎为零（验证闭环无法执行）

**必须先完成方案 P0 阶段，方可启动自动派发。**

## 四、与方案 P0 阶段的对应

方案第六节定义了 P0 环境准备（0.5 天），验收标准是"脚本能手动派发一个写 README 的 Agent 并取回 result.json"。对照现状，P0 需补齐的工作：

| P0 任务 | 现状 | 工作量 |
|---------|------|--------|
| `git init` + 首次提交 + 推送远程 | 未初始化 | 10 分钟 |
| 建 `AGENTS.md`（构建/测试/规范说明） | 不存在 | 需从技术规约提炼 |
| 建 `contracts.md`（模块间契约） | 不存在 | 需从功能说明书提炼 |
| 建 `TASKS.md`（M1~M10 依赖排序） | 不存在 | 需从一期功能说明书提炼 |
| 建 `tasks/` + `artifacts/` 目录 | 不存在 | 1 分钟 |
| 生成 `CURSOR_API_KEY` + `GITHUB_TOKEN` | 未配置 | 需在 Cursor Dashboard + GitHub 生成 |
| 写 `cursor_client.sh`（派发/轮询/取结果） | 不存在 | 半天 |
| 补 `mvnw` wrapper + 根级 Makefile | 有 Maven 无 wrapper | 30 分钟 |
| 从技术规约抽取 `api-design.md` / `data-model.md` | 内嵌规约中 | 2 小时 |

## 五、建议的落地顺序

1. **先 git init**（命脉，1 步解锁后续所有工作）
2. **建协作骨架**：`AGENTS.md` + `contracts.md` + `TASKS.md` + `tasks/` + `artifacts/`
3. **补构建工具**：`mvnw` wrapper + 根级 `Makefile`（统一 `make test` / `make build`）
4. **抽取独立文档**：`docs/api-design.md` + `docs/data-model.md`
5. **搭测试框架**：后端补 `spring-boot-starter-test` 样例；前端加 `vitest`；确认 `pytest` 可跑
6. **配置凭证与脚本**：`CURSOR_API_KEY` + `GITHUB_TOKEN` + `cursor_client.sh`
7. **跑 P0 验收**：手动派发一个"写 README"的 Agent，确认 result.json 回传

> 以上 1~4 可在半天内完成，5 是最大变量（取决于业务模块的测试覆盖目标），6~7 半天。总计约 1~1.5 天可达到 P0 验收线。
